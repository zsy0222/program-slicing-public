# J 组切片代码审查与工具选择

日期：2026-09-27。范围：当前本地代码、2026-09-26 保存的正式任务/准备记录、工具官方资料。性质：只读诊断与下一版设计建议；没有重跑 Defects4J、修改历史队列、安装工具或调用模型。WALA/JOANA 尚未在本项目验证。

## 1. 研究问题与推荐

研究对象是“给模型提供工具生成的程序依赖切片，是否改善可测的故障理解与修复表现”。工具应按依赖语义、切片准则、可追溯性和覆盖率选择，选择过程在观察新批模型结果之前完成。负结果也能回答研究问题，不能以模型修复率选择工具或事后筛选有利缺陷。

推荐下一版以 **WALA 静态后向切片 + Slicer4J 动态后向切片** 为主；首先做相同源码包下的切片标记对照，再单独研究切片抽取的上下文压缩效果。JOANA 留作第二静态实现的敏感性分析候选。此为实施优先级建议，不是本地兼容性已通过的结论。

两个维度须分清：静态/动态区分是否利用特定执行；前向/后向区分依赖遍历方向。静态后向和动态后向可以配对。所谓“双向切片”必须进一步定义为前后向并集或双端点 chop，不能把它与静态、动态当作三个平行类别。

现有组的操作定义：J-A=主要生产文件；J-B=栈帧所在完整方法；J-C=跨文件动态切片源码行集合；J-D=J-B 源码加该动态切片源码集合。没有静态依赖切片组，也没有前后向组合组。切片结果被按文件/行号排序去重，没有向模型提供事件顺序、依赖边或运行时值。

具体例子：Closure-125 的 J-B 方法只有 4 行，动态切片有 3,142 行，其中 3,140 行不在该方法内；Chart-18 的方法为 15 行，切片为 34 行，其中 29 行在方法外。因此旧 J-B/J-D 可以研究这种“增加动态切片源码块”的实际输入策略，不能单独归因于同一源码上的相关性标记，也不能据这些数字归因于切片质量差。

## 3. 代码发现和优先级

### P1：切片准则只来自生产异常栈帧

`prepare_j_full_scale_slices.py:127` 从栈中选第一个能匹配生产源码的帧；`:274`–`:284` 无该帧就退出。普通断言比较发生于测试方法，失败时调用的生产方法可能已经返回，因而不存在相应生产栈帧。推荐支持测试断言位置作为准则，并将测试类纳入可插桩/分析的应用类范围。当前 `:313`–`:329` 只打包第一个生产 class 目录作为插桩 jar，测试 class jar 放在依赖目录；仅改 `-b` 的行号仍不足以保证测试断言被插桩。

### P1：同一 source_view 不等于相同可见源码

`build_j_context_views.py:112`–`:132` 将每个切片成员的原始源码一起加入 J-D，包括其他方法与文件。`preflight_j_model_jobs.py:99` 验证去除整个切片字段后 B/D 相同，但不检查字段内是否新增源码。下一版纯标记对照应固定源码包，切片只引用该包中的 source ID；另设源码检索/压缩对照评价跨方法扩充的效果。

### P1：编辑范围被限定为异常位置所在方法

`build_j_context_views.py:121` 将所有组编辑权限设为同一方法。公平性在四组内成立，但故障发生位置未必是根因或合理修复位置。观察到跨方法依赖也无法编辑相应方法。新的可编辑范围须由 buggy 版本和预注册策略独立确定，不能根据 fixed diff 指定；所有组使用同一范围。若仍采用方法内修复，结论应明确限定该场景。

### P2：成功门槛不足以证明切片对应目标失败执行

`prepare_j_full_scale_slices.py:352` 以四个文件非空且有映射节点判为 ready，没有同时要求 slicer 返回码、timeout、插桩后同一 trigger 的相同失败签名、目标事件可定位和 trace 完整性。应新增这些门槛并区分 `trace_failure_changed`、`criterion_not_executed`、`mapping_incomplete`、`tool_failed` 等；原包装命令返回 0 也不能替代内部步骤检查。当前 saved-ready 无非零退出/超时，是本次已验证的有限好消息。

### P2：准则和源码映射信息损失

`prepare_j_full_scale_slices.py:327` 把内部类 `$...` 去掉再传给 slicer；文件定位可以用外部类源文件，运行时准则却需要保留实际二进制类和方法身份。3 个已纳入案例存在内部类帧，需要对工具实际选中的事件进行核对，暂不宣称这些切片错误。

`build_j_context_views.py:98`–`:117` 对原始节点解析、映射并按源码行去重；未匹配正则的行直接跳过。后续应统计未解析非空行并保留 bytecode/Jimple、线程、发生次数、源位置映射；同一源码行可含多个指令，一行多次执行也不是同一动态事件。32 例有 unmapped 记录，需要分类，合成节点/库模型无法映射不自动等同切片失效。

### 已有正确约束应保留

输入按匿名缺陷编号配对；共同失败投影与编辑权限一致；J-C 没有偷偷附完整方法；F2 类参考修复信息未因本次审查加入任何队列。既有视图测试 2/2 与输入预检测试 5/5 本次通过。这些测试验证结构约束，不验证程序依赖语义；本次没有对所有输入内容重新证明完全无信息泄漏。

## 4. 工具选择依据

| 工具 | 用途及优势 | 本项目选择条件 |
|---|---|---|
| WALA | 基于 SDG 的上下文敏感切片；提供后向/前向切片接口，可配置数据与控制依赖 | 首选静态候选，便于冻结入口、调用图/指针分析配置及导出源映射；先验证 Defects4J 兼容性 |
| Slicer4J | 从执行语句生成动态后向切片，已有本项目原始记录，可导出 Jimple 与源映射 | 首选动态候选；补齐测试断言准则、插桩保真、事件选择和成功门槛 |
| JOANA | 基于 WALA/SDG，支持 slicing/chopping，侧重信息流分析 | 作为静态结果的第二实现或后续 chop 候选；需核对其字节码、反射和环境支持，不直接假定全库可用 |

WALA 主配置建议保留 `DataDependenceOptions.FULL`、`ControlDependenceOptions.FULL`；具体调用图算法（例如 0-1-CFA）、入口/反射配置、库排除和版本在开发阶段验证后冻结。其官方文档明确 FULL 与 NO_HEAP 等选项意义不同。若为了资源改用 thin slice，应单独列组并报告；不能把去除堆依赖的结果继续标为相同静态切片。[WALA 官方切片文档](https://github.com/wala/WALA/wiki/Slicer)

Slicer4J 官方接口 `-b` 是后向准则，`-d/-c/-once` 会改变所跟踪的依赖/范围；主实验使用递归数据加控制依赖，并记录实际工具提交与参数。官方 README 标注 Java/JRE 条件，源映射依赖调试行号；应分别记录分析器运行 JDK、被测程序编译目标和字节码版本。[Slicer4J 官方仓库](https://github.com/resess/Slicer4J)

工具论文使用失败测试断言作为 Defects4J 切片准则，支持本项目扩展准则定位的方向；论文也讨论运行时生成类及插桩改变并发行为的限制，不能直接把工具论文本身当作本项目兼容性验证。[Slicer4J 原论文](https://people.ece.ubc.ca/mjulia/publications/Slicer4J_2021.pdf)

JOANA 官方项目页说明其 SDG、slicing/chopping 与语言支持范围；主用途是信息流验证。本项目若采用，需要验证调试切片输出及成本，不能把其安全性证明自动转化为修复证据可靠性保证。[JOANA 官方项目页](https://pp.ipd.kit.edu/projects/joana/)

**跨工具解释边界**：WALA/Slicer4J 的结果差异同时包含静态/动态策略、堆和库建模、实现配置的差异。主结论可写“这两种冻结实现的证据对任务表现的影响”；若要归因于静态/动态这一维度本身，应增加共享表示的实现对照或第二工具的复核。在开发阶段按覆盖率/依赖正确性/成本选工具，禁止按模型修复收益选工具。

## 5. 下一版最有解释力的对照

建议新批次名 `J-slicing-v2`，不重命名或覆盖旧 J-A–J-D。分成两个实验，分别回答信息标记作用与上下文压缩作用。

### 实验一：固定源码，比较依赖标记

先为每例冻结一个各组完全相同的可见源码包 C。C 来自 buggy 源码和不依赖组别的定位/检索策略，不能用某组切片或参考补丁决定 C；源码包的文件、行号、代码和可编辑范围统一。若仅使用一组固定候选方法，主张也限定在该源码范围内。超预算案例预先分层，不能临时按不同组截断。

| 条件 | 模型输入 | 回答的问题 |
|---|---|---|
| J2-Base | C + 同一失败信息/切片准则，无成员提示 | 基准 |
| J2-Static | Base + 静态后向成员标记 | 静态依赖信息的增量 |
| J2-Dynamic | Base + 动态后向成员标记 | 动态依赖信息的增量 |
| J2-Executed | Base + 同次失败执行的覆盖行标记 | 执行相关性相对依赖筛选的区别 |

每组使用相同行表模板；每行同一位置保存固定格式成员状态，证据组不得额外重复源码或补写根因。Base 使用明确的无提示状态，不能把全 0 误解为“分析证明全部不相关”。统计真实 token 数；相同模板不保证 tokenizer 的精确等长。

主比较：Static–Base、Dynamic–Base。Dynamic–Executed 检查依赖筛选是否比“这行执行过”提供额外价值；Static–Dynamic 为次要比较。若要进一步区分成员数量/醒目提示效应，预设等数量安慰剂标记分别匹配 Static、Dynamic：独立随机种子，在相同源码范围抽取，保留共同准则，不按参考补丁或模型结果挑行。安慰剂仅为诊断条件，不能与真实程序依赖混称。

完整跨方法图在后台计算，再统一投影到 C；记录 C 外成员数量、库节点、合成节点与映射失败，投影结果明确叫“固定源码范围内成员标记”。主实验不要求拿到可独立编译的切片；它测的是阅读证据。依赖边和运行时值暂不提供，以免 Static 与 Dynamic 又改变不同的信息类型。

### 实验二：固定预算，比较源码抽取

单独比较相同输入预算下的普通 AST 方法/邻近上下文检索、静态切片引导检索、动态切片引导检索、执行覆盖引导检索。这里不同代码内容正是处理差异，测“在有限上下文下哪种选择策略更实用”。统一文件排序、源码行号、必要声明/括号/签名补全策略，并分别标注 slice member 与仅为可读性补入的 context。

模型可编辑范围独立于所见切片统一冻结，使用同一种行编辑接口；报告未展示的可编辑行比例。提供更广源码可能提高可修复性，给更少源码也可能因信息不足增加补丁格式失败；这些属于压缩策略的总效果，不能再声称隔离了“标记本身”。保留完整源码无切片基线作为成本/表现参照，按 token 分层解释，不用不同长度的单一总修复率直接归因。

## 6. 同一切片准则如何落地

1. 从冻结的 failing test 列表按确定性规则选一个 trigger；所有组共享该测试、输入和同一故障报告。静态分析可以使用该测试作为调用图入口，但须称为“测试入口限定的静态切片”，仍包含静态分析允许的多条路径，不伪称独立于测试的全程序切片。
2. 异常型以目标异常事件、实际类/方法/字节码位置为准；断言型以失败断言调用及其受检值为准。断言在测试方法内时，分析范围须含测试包装与生产代码。测试代码可以只在后台用于依赖追踪，模型共同看到的测试信息必须一致。
3. 冻结准则变量集合。若 Slicer4J 当前包装器只能从一行全部使用变量起切，WALA 也要按对应语句集合对齐；不能让一边针对 actual，一边混入 expected/message。无法对齐的案例单列不支持。
4. 动态准则还需线程、事件序号/调用上下文和失败发生的那次执行。同一行循环多次不能任取最后一个事件而不核对失败位置；静态端对应同一源语句/IR 指令集合。记录多指令合并规则。
5. 包含控制依赖、堆字段/数组、跨方法参数/返回依赖。外部库与 native 摘要、反射处理规则预先冻结并审计。映射出源代码后再按统一规则呈现，禁止用 fixed diff 反向选准则。

双向方案暂不放主对照。前向用于影响传播，后向用于追溯影响该失败观察的依赖；若后续做 chop，需一个独立于参考修复的来源准则与失败观察终点，采用工具定义的可实现路径算法。不能把任意前后向集合的交/并直接命名为更精确的动态切片。

## 7. 评价与下一步实施顺序

理解与修复分别发起独立请求，统一模型版本/参数/调用次数，交错随机组别顺序并保存时间。理解报告位置 Top-k、执行可核对的状态/分支预测和行为保留判断；开放式根因解释按冻结规则双人匿名盲评。开发者修改行只作辅助定位指标，允许多种正确补丁。状态预测题的答案/轨迹值不得直接出现在某个证据组输入中。

修复分层报告格式有效、编译、trigger、完整模块测试，通过完整测试称测试充分性。不得用修复通过替代理解评分。统计独立缺陷配对差值、置信区间；单次二元配对可使用精确 McNemar，重复尝试按 bug 聚合/聚类 bootstrap，不把重复当独立样本。预注册多重比较与主要指标；50 例是规模选择，不自动保证功效。

分别给出共同工具成功子集的条件效应与原冻结样本的覆盖/端到端效应；工具失败不算模型修复失败。若系统设计支持 fallback，明确使用同一无切片 fallback 并独立报告其策略效果。避免只按“切片包含参考修改行”纳入。已观察的 43 例可用于诊断与开发，新确认集须另作未暴露划分。

实施优先次序：

1. 保留旧批次；为新协议创建 `resolve_j_criterion_v2`，支持断言/异常、测试插桩和精确事件标识；先在不进入正式模型评价的 12 个分层开发案例检查，其中覆盖断言/异常及多个项目。
2. 实现 Slicer4J 运行完整性门槛与 WALA 静态适配器；输出统一 evidence manifest。以带已知依赖的小型 Java 测试检验字段别名、数组、分支、循环、多次调用、异常处理、跨方法返回与内部类，未执行分支应在静态/动态模式下呈现预期差异。
3. 冻结工具 commit、依赖版本、类路径、字节码目标、根入口、指针分析、边类型、资源上限和库模型。运行失败不临时降级后伪装成同组成功；记录覆盖与成本后完成最终工具选型。
4. 建立公共源码包与四种标记视图，预检全部源码字节/编辑范围相同、标记引用合法且原始源映射可追溯。额外行、缺失行、未映射节点、截断和上下文 token 全部保存。
5. 在独立确认样本冻结输入、评分与统计协议后，再进入已授权范围内的模型阶段。本次审查没有发起新模型调用。

以上修改属于下一版实施清单；本轮只新增了诊断脚本、机器审计结果和本报告，没有修改原切片运行器。
