# 研究发展全过程：从 Chop4LLM 到 LLM 驱动的 Error Invariant 语义理解

> 研究起始: 2026年初 | 最后更新: 2026-07-18
> 当前阶段: Phase 4 — LLM 深度阅读抽象解释中间表示

---

## 第一章：研究起点 — 程序切片与 Chop (2026年初–2026年5月)

### 1.1 系统学习程序切片

研究始于对程序切片这一经典程序分析技术的系统学习。阅读了领域奠基性文献：

- **Weiser (1984)** — 程序切片原始定义，slicing criterion ⟨l, V⟩ 概念
- **Ferrante, Ottenstein & Warren (1987)** — 引入 PDG，后支配形式化控制依赖
- **Korel & Laski (1988)** — 首个动态切片，仅关注实际执行路径

### 1.2 发现核心局限

动态后向切片的本质问题：**它是依赖关系的传递闭包**。后向切片将一万行缩减到五百行，但不会在 bug 行停下来——它沿依赖链一直追溯到程序入口。程序员仍需通读整个切片。

### 1.3 发现 Chop (Jackson & Rollins 1994)

Chop 的核心思想：引入第二个锚点 (source)，将单向追溯变为两个锚点间的定向搜索。

**传统取交集的缺陷**: 节点 A 在前向切片中因某条路径而在后向切片中因另一条路径，两者没有实际连接。

**Chop 算法**: Phase 1 前向可达子图 → Phase 2 在受限子图内做后向可达。

**关键洞察**: source 是人工输入——若能用 LLM 自动推测 source 候选，Chop 就能自动化。

### 1.4 确立方向: Chop + LLM

将 Chop 与 LLM 结合，让 LLM 自动生成 source 候选点，实现自动化双向切片故障定位。

## 第二章：Chop4LLM — 自研工具阶段 (2026年5月–6月)

### 2.1 参考工具学习

- **code2prompt** (GitHub 7.3k Stars): Handlebars 模板系统
- **GitIngest** (GitHub 4k+ Stars): 极简 API 设计
- **IBM CLDK** (ICSE 2025): 程序分析→LLM 桥梁架构

### 2.2 Chop4LLM 实现

开发了 Python 工具实现基于 PDG 的双向程序切片 + LLM 提示词生成。

**技术架构**:
- 解析层: javalang (Java AST) → 语句/变量/控制结构提取
- PDG 构建: CFG → 后支配分析 (控制依赖) → 到达定值 GEN/KILL/IN/OUT 迭代不动点 (数据依赖)
- 切片层: forward_slice → backward_slice → chop (两阶段受限可达性)
- 格式化层: 模板系统 + 依赖标注代码 + 结构化调试引导问题                                                                                        

**验证结果** (4个测试用例):
| 测试用例 | 原始语句 | 后向切片 | Chop | 缩减率 |
|---------|---------|---------|------|-------|
| Discount Bug | 8 | 6 (25%) | **3 (62.5%)** | Chop > 后向 |
| 线性 def-use | 4 | 4 (0%) | 4 (0%) | 全保留 |
| if-else 分支 | 5 | 4 (20%) | 4 (20%) | 正确保留分支 |
| 无 bug 案例 | 5 | 5 (0%) | 5 (0%) | 正确全相关 |

**验证通过的 PDG 特性**: 控制依赖 (if条件→被控语句)、数据依赖 (def-use 链非变量名匹配)、KILL 机制 (重定义截断)、if-else 双分支正确保留。

### 2.3 Chop4LLM 的局限

- PDG 切片 + LLM 分析是两个**独立步骤**，非统一框架
- 切片质量受限于 PDG 构建精度
- 传统 PDG 需要全程序指针分析 (O(n³))，无法处理不可编译代码
- Chop 的 source 仍需人工指定，LLM 辅助有限

## 第三章：SWP — LLM 作为切片引擎 (2026年6月底–7月初)

### 3.1 方向转变

**旧思路**: PDG 算法做切片 + LLM 做分析（两个独立步骤）

**新思路**: 不写传统 PDG 切片算法，设计结构化切片推理工作流范式 (Slicing Workflow Paradigm, SWP)，让 LLM 自己按范式一步步推理依赖关系、输出切片代码。

**研究问题**: 一个精心设计的结构化推理范式能否让 LLM 产出与传统 PDG 算法精度相当的切片？

### 3.2 关键论文调研

系统搜索了 LLM 做程序切片的现有工作：

| 工作 | 方法 | 核心结果 |
|------|------|---------|
| **SliceMate** (2025.07) | 三 Agent 协作 (Synthesis+Verification+Refinement) | 准确率 +22%, F1 +28% |
| **SLICEFORMER** (ACL 2026) | Seq2seq + 数据流感知预训练 | ExactMatch +22% |
| **SLICET5** (2025.09) | Copy Mechanism + 约束解码 | ExactMatch +27% |
| **NS-Slicer** (OOPSLA 2024) | CodeBERT 逐语句分类 | F1=97.41% |
| **Shahandashti** (COMPSAC 2025) | 裸调 GPT-4o 做切片 | 仅 60.8% 准确率 |

### 3.3 关键洞察：LLM 语义切片 vs 传统 PDG 可达性

**传统方法的核心瓶颈**: 确定跨函数依赖需要调用图 + 指针分析 → 全程序 O(n³) → 工程不实用。

**LLM 的优势**:
- 绕过类型决议诅咒 (无需精确类型分析)
- 不可编译代码也能切
- 语义消歧 (区分语法有关但逻辑无关的语句)
- 按需付费 (无全程序入场费)
- 语言无关
- 可解释性 (自然语言解释每句为何被包含)

**LLM 的劣势**: 不 sound、不确定、长程序受 context window 限制。

**一句话总结**: **传统方法用数学精确性换取工程不实用；LLM 用语义推断换取工程实用。Debug 场景天然容忍不完美。**

### 3.4 SWOT 面临的问题

- **与 SliceMate 重叠度高**: SliceMate 已用三 Agent 做切片引擎，SWP 差异化不足
- **SliceMate 仅做后向切片**: 但他们的结果已经很强 (+22% accuracy)
- **LLM 直接做切片的天花板**: Shahandashti 2025 显示裸调 LLM 仅 60.8%——SWP 范式能否显著超越？

## 第四章：级联混合切片 — 断言引导 (2026年7月初–7月中)

### 4.1 从 SWP 转向混合架构

**问题**: SliceMate 已占领 "LLM 做切片引擎" 赛道。需要新的差异化定位。

**新方向**: 不把 LLM 当切片引擎，而是把 LLM 嵌入传统故障定位流程——用 LLM 语义推理补充传统分析的盲点。

### 4.2 级联混合切片框架 (原方案)

**核心架构**:
```
Phase 0: 断言插桩 (ASSERTIFY)
Phase 1: 动态后向源点定位 (沿 trace 扫描断言 PASS/FAIL)
Phase 2: 静态前向路径验证 (assert PASS→裁剪, assert FAIL→保留)
```

**与 Zhang 2007 MPS 的对比**:
| 维度 | Zhang 2007 MPS | 级联混合 |
|------|---------------|---------|
| 引擎 | 纯动态 DDG (2-3 数量级减速) | LLM 语义 + 静态分析 |
| 输入 | 需要 3 个准则 | 只需 sink |
| 完备性 | 受限于 trace | 阶段 2 覆盖所有路径 |
| 可解释性 | 行号集合 | 逐语句断言证据 |

**关键设计选择**:
- **级联而非交集**: Phase 1 输出是 Phase 2 输入，信息单向流动
- **断言作为 Ground Truth**: 运行时客观事实，独立于推理引擎
- **LLM 角色边界**: 仅限 Phase 1 源点定位，Phase 2 使用确定性静态分析

### 4.3 方案评审后的核心质疑

在与学长讨论后识别出以下问题：

**问题 1: 断言依赖脆弱**
- 依赖 ASSERTIFY (LLM 工具) 生成断言 → LLM 工具生成断言的准确性本身未经评估
- 断言覆盖率不足时框架退化
- 断言插桩修改源码 → 改变了被调试程序的行为

**问题 2: 与 Dimovski 2024 的定位冲突**
- Dimovski 已做了 "后向-前向迭代精化" → 同样的范式
- Dimovski 不需要运行时、不需要断言、有形式化保证
- 用断言替换抽象解释 → 看起来像降级而非升级

**问题 3: LLM 仅做分类器的创新性不足**
- "引入 LLM 分析 Dimovski 的切片结果" → 本质是 LLM 当二分类器
- 没有让 LLM 真正理解形式分析的过程
- 单向：Dimovski → LLM，没有反馈回路

## 第五章：当前方向 — LLM 深度阅读 Error Invariant 轨迹 (2026年7月18日)

### 5.1 方向再转变

**核心认知**: 舍弃断言，换用 Dimovski 的抽象解释作为确定性骨干。LLM 不再是切片结果的后处理器，而是 **Error Invariant 轨迹的深度语义理解者**。

### 5.2 为什么选择 Dimovski

**Dimovski 是唯一产出结构化中间表示的工具**:

| 工具 | 输出 | LLM 能读吗 |
|------|------|:---:|
| Ochiai / Tarantula | 可疑度分数 | ❌ 数字无语义 |
| Zhang 2007 MPS | 行号列表 | ❌ 和直接读代码没区别 |
| SliceMate | 行号列表 | ❌ 黑盒无中间过程 |
| BugAssist | 布尔核 | ❌ 对人类和 LLM 都不可读 |
| **Dimovski** | **Error Invariant 序列** | ✅ 数学约束+语义可读+位置排列 |

Error Invariant 的三个关键属性：
1. **数学精确定义** — 可被形式方法操作
2. **人类可解释** — `[y = x + 1, x ≥ 5]` 可直接理解
3. **沿程序位置排列** — 形成演化轨迹，可追踪错误传播

### 5.3 Error Invariant 中被 Dimovski 浪费的信息

Dimovski 只用 Error Invariant 做了一件事：对比相邻位置的 invariant 是否相同 → 决定语句是否相关。

但 invariant 内部包含丰富的传播语义：
- 哪个变量**新进入**了错误条件（首次出现在 invariant 中）
- 哪个变量**退出**了错误条件（从 invariant 中消失）
- 变量间关系如何**演变** (`x ≥ 5` → `z = 2*x` 的转变)
- 错误条件的"**强度**"变化（约束变紧/变松）
- **关键转折点**——invariant 发生质变的位置

### 5.4 LLM 从 Invariant 轨迹中能做的事

**① 语义翻译**: 将 `[y = x + 1, x ≥ 5]` 翻译为 "y 等于 x 加 1，且 x 至少为 5。这意味着..."

**② 质变检测**: 找到 invariant 发生语义性质改变的位置——Dimovski 只知道 "变了"，不知道 "变的是什么意思"

**③ 缺失推断**: LLM 观察 invariant 轨迹中的语义断裂，建议 Dimovski 自己无法发现的精化谓词

**④ 因果链重构**: 从 invariant 轨迹中提取 "错误从 X 起源，经过 Y 转折，最终在 Z 表现为失败" 的完整叙事

**⑤ 反馈精化**: LLM 建议的补充谓词 → 加入 ℙ → Dimovski 重新 BDD 精化 → 循环

### 5.5 四阶段架构

```
INPUT: 源代码 + 错误位置 (assert失败点)
        │
        ▼
┌─────────────────────────────────────────────────────────┐
│ PHASE 1: Dimovski 分析 (确定性骨干)                       │
│   迭代后向-前向抽象解释 → 全位置 Error Invariant 序列      │
│   + 初始语句级语义切片                                    │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│ PHASE 2: LLM 深度阅读 Error Invariant 轨迹 ★ 核心贡献     │
│   任务①: 语义翻译 (invariant → 因果描述)                  │
│   任务②: 质变检测 (找到 invariant 质变的位置)              │
│   任务③: 缺失推断 (建议 Dimovski 无法发现的精化谓词)       │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│ PHASE 3: 反馈精化 (双向增强 ★)                            │
│   LLM 建议的谓词 → ℙ → Dimovski 重新 BDD 精化             │
│   → 循环至 LLM 不再建议新谓词或 invariant 稳定              │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│ PHASE 4: 因果链重构 + 可读输出                            │
│   基于精化后 invariant 轨迹:                               │
│   ● 错误起源点 + 语义理由                                  │
│   ● 传播路径关键转折点 + invariant 证据                    │
│   ● 修复建议 (指向具体 invariant 变化点)                    │
│   ● 置信度 (invariant 覆盖完整度)                           │
└─────────────────────────────────────────────────────────┘
```

### 5.6 与之前方案的对比

| 维度 | 原方案 (断言混合) | 当前方案 (Invariant+LLM) |
|------|-----------------|------------------------|
| 静态骨干 | Phase 2 静态前向 (自研) | Dimovski 抽象解释 (已有) |
| Ground Truth | 运行时断言 PASS/FAIL | Error Invariant 数学约束 |
| 需要执行 | 是 (失败测试+断言插桩) | **否** (纯静态) |
| LLM 角色 | Phase 1 源点定位辅助 | **深度理解 invariant 轨迹** |
| LLM-分析关系 | 单向 (分析→LLM分类) | **双向** (LLM 反馈精化) |
| 创新点 | 级联架构 | **LLM 首次阅读抽象解释中间表示** |

### 5.7 理论贡献 (当前版本)

1. **Error Invariant 作为半形式化语义接口**: 首次提出将抽象解释的中间表示作为 LLM 与形式方法之间的共享语言，使 LLM 能够 "读懂" 形式分析的内部推理过程。

2. **LLM 驱动的谓词发现**: LLM 不再是事后分类器，而是主动引导 Dimovski 精化过程的 "语义顾问"——根据对 invariant 轨迹的语义理解，建议形式分析自身无法发现的精化谓词。

3. **双向反馈架构**: 形式分析提供可验证的结构 (soundness)，LLM 提供语义理解 (precision + explainability)，两者通过 invariant 轨迹在循环中互相增强。

4. **从不变量序列到因果叙事**: LLM 不是解释代码，而是解释 invariant 的演变轨迹——更精炼、更聚焦于 "错误如何传播"。
